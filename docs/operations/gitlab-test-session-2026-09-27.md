## 已定位的通用问题

### 1. 滚轮方向与 Electron 原生事件相反（已复现）

`agent-action-runtime.ts` 的 `scrollDeltaForDirection` 把 down 编码为正 deltaY；`agent-interaction-executor.ts` 又原样传给 Electron `sendInputEvent(mouseWheel)`。在当前 Electron 隔离实验中，传 `deltaY=100` 产生可信 DOM wheel `deltaY=-100`，内部容器从 scrollTop=700 变成 600；传 `deltaY=-100` 则产生 DOM wheel `deltaY=100`，内部容器变成 800。

因此“向下”在原生滚轮路径实际往上；页面已经在顶部时不会移动。这不是 GitLab 专用问题。应在输入适配边界明确区分 DOM/CDP 位移与 Electron 原生滚轮方向，不能同时无差别反转后续 DOM scrollBy 的参数。

Electron 的原生事件合同参见 [MouseWheelInputEvent](https://www.electronjs.org/docs/latest/api/structures/mouse-wheel-input-event)。上述符号判断来自本机实测，而非仅凭接口字段名推断。

### 2. 内部滚动容器不受自动滚动正确处理（已复现）

`agent-interaction-executor.ts` 的 `scrollAgentViewportByDelta` 只比较 window.scrollX/scrollY；没变化时只调用 window.scrollBy。`ensureAgentElementVisible` 基于控件坐标调用这条路径，没有沿真实元素的滚动祖先逐层暴露目标。

生产函数 + 独立 Electron 页面复现结果：

| 场景 | 状态 | 结果 |
| --- | --- | --- |
| 整个窗口的长页面，向下滚 500 | 补救成功 | 原生滚轮未向下，靠 window.scrollBy 到 500 |
| 整个窗口的长页面，点击屏外按钮 | 正常 | 自动滚动后真实点击成功 |
| 固定窗口、内部 overflow:auto 容器，向下滚 500 | 异常 | 容器保持 0，返回 scrolled=false |
| 相同内部容器，点击屏外按钮 | 异常 | 返回与真实 GitLab 相同的 targetNotActionable，按钮未收到点击 |

即使修正滚轮方向，仍要修复容器级进度判断；内部容器滚动本来就可能不改变 window.scrollY。不能只改正负号就宣称根治。

复现脚本和日志位于 `/home/xu-yuanhao/.cache/lyra-latest-gitlab-20260927/scroll-repro.mts` 和 `scroll-repro.log`。这些是隔离诊断，没有改动产品或真实网页。

### 3. 地图与失败恢复信息不一致（已定位）

地图明确写着 `[offscreen; act scrolls to target]`，但自动滚动没有覆盖上述内部容器。5 次点击失败都返回同一个“detached, disabled, moving, or covered”笼统错误；准备脚本已有部分原因字段，却在执行器转换为 null 后丢失，最终建议仍为重新 map。

同一按钮引用在 PageUp / PageDown 后最终成功，说明这些失败并不意味着必须取得新引用。盲目重取地图无法修复滚动执行问题。部分仍在页面中的控件又被 covered 过滤掉，当前回包只给出数量，不足以告诉 agent 怎样找回、应滚哪个容器。

### 4. 新生成的凭证没有经过安全引用链路（已定位）

第 51 次工具返回的地图把只读 token 输入框标为“unnamed input”，同时输出完整值。第 52 次工具把它直接拼入 HTTPS clone URL。会话数据中确认模型的工具调用和工具结果存在完整 token；不是最终回复不显示就等于安全引用。

当前 `agent-affordance-lists.ts` 会把字段的 textSnippet 当作 value 展示，而没有覆盖这种新凭证输出。需要贯通网页读取、工具结果、模型上下文、shell 使用和日志保存的安全引用机制；仅在最终回答里隐藏 token 或仅在 GitLab 页面加特殊规则都不能解决。

### 5. 等待条件猜错，已有结果仍等待（会话证据）

两次 browser_wait 分别等待 `Choose an account` 和 `Clone`，实际结果已经是登录后的主页、已进入的仓库页面，但返回 completion=unknown。两次工具分别耗时 11.335 秒、10.957 秒。条件应该来自已观察到的状态或目标变化，不能把猜测的 UI 文本当作唯一完成条件。

### 6. 完成后的清理扩张与错误总结（会话证据）

删除 clone 的动作本身成功。随后 agent 额外遍历 `/tmp` 和整个家目录找 `glpat-`；`grep -v .lyra` 只是过滤输出，并没有阻止前面的 grep 读取该目录。命令在 30 秒预算结束后继续后台运行。调查时 shell PID 41149 及其 grep 子进程仍存在，已运行超过 6 分钟，grep 的进程生命周期平均 CPU 约 66%。调查未终止该进程。

最终回复同时声称“家目录和 /tmp 无我方残留”又承认扫描尚未完成，前一结论没有成立依据。它还把 Chromium 临时文件里的两次 `glpat-` 前缀匹配当作完整新 token。此次只做内存中的精确比对：文件含前缀，但没有此次完整 token 的 ASCII 或 UTF-16LE 字节序列；不能从前缀推断 token 泄漏，也不能据此保证重启就清除。
