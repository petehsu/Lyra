# QQ 空间输入与发布调查

2026-09-26，仅调查；本轮没有修改产品代码或操作用户 QQ 空间。会话 `session-cf9725e0-63af-48ff-8c15-0cf57d51a901`，标题“打开QQ空间把登录二维码显示在聊天界面”。重点是 11:48:36 开始的“禁止截图、发一条动态”请求。时间为 America/New_York（UTC−4）。

## 结论

动态最终有发布成功的页面证据，但输入流程存在真实缺陷：三次输入均使用 `execCommand.insertText`。首次返回的内容是“Lyra —— 目前为止非视觉方案里最快的网页操作方案之一。说点儿什么吧”，工具却报告“The field holds the text”。

截图中灰色文案与占位提示状态未正确退出的方向吻合。不能仅凭截图认定它直接修改了 HTML `placeholder` 属性；我们的输入代码实际是聚焦可编辑元素、设置选区、执行网页内编辑命令，再补发事件。现有记录没有保存 QQ 空间当时完整 DOM 和回调调用栈，不能证明最终灰色残留由哪一个 QQ 空间回调生成。

## 已确认问题与定位

1. **未经过编辑器激活流程。** `agent-focus-input-controller.ts:1199` 明确跳过预备点击，`:671` 只做 DOM focus，`:683` 调用 `document.execCommand`。这保护了已有选区，却不适用于所有首次进入或延迟初始化的编辑器。它没有执行真实点击/按键链来让站点完成占位清理或切换编辑宿主。
2. **重复输入事件。** `:689` 在 execCommand 已触发 input 后，继续通过 `:489` 人工发送 input/change。隔离 Chromium 复现实测是一条可信 input、另一条非可信 input、一个非可信 change。实际 QQ 空间是否因此重复执行了内部回调，未取得事件记录，不能直接下结论。
3. **成功判定过弱。** `:701` 对默认追加输入主要检查 `after !== before`，读取的是 textContent/value，不验证站点编辑状态已经接受文案。即使提示文字仍留在里面，只要 DOM 文本变了就成功。30ms 后虽刷新地图，回包的成功和 inputValuePreview 仍来自之前的插入结果。
4. **map 和 read 的 iframe 范围不一致。** `agent-page-controller.ts:150` 的普通文本读取在顶层 webContents 执行；记录里说说页的 read 仅有导航，而 map 能读到 iframe 中编辑器和已发布动态。只针对 waitTargetRef 的分支有显式 frame 路由。
5. **动态页面让分页反复重置。** `agent-map-presentation.ts:64` 把当前匹配目标的 targetRef、label、region 一起纳入游标指纹。两次翻页被拒绝，其中第二次使用刚返回的游标：索引从 150 变成 146。拒绝旧索引能保护目标正确性，但没有提供继续阅读稳定快照的办法，agent 只能重来。

## 修复方向与验收边界

应修复输入执行层与编辑状态验证，不靠硬编码“说点儿什么吧”、直接修改占位属性或无条件清空内容。首次进入编辑器时完成真实激活并重新解析实际编辑宿主；已有有效选区时保留选区。走浏览器输入通道，避免重复补发 input。插入后确认当前仍存活的编辑宿主接受了内容，并把失败明确返回给 agent。

随后统一 read/map 的 frame 范围，让地图分页可以基于稳定快照继续读取，同时保留执行动作前的实时目标校验。

真实场景验收应是：QQ 空间空编辑器 → 正常进入可编辑状态 → 输入一次，提示消失、文案不夹带提示 → 失焦/聚焦后仍正确 → 若用户授权发布，再提交一次并确认列表新增。还需覆盖 Gmail 的已有选区/加粗，防止为了激活新编辑器破坏既有编辑行为。本次没有实施这些修复。
