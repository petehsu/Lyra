# 工作区网页与外侧界面的焦点隔离

2026-09-27。用户报告：工作区网页打开菜单后，点击外侧界面会把网页菜单关闭。

## 固定验收动作

1. 在工作区网页打开一个依赖焦点保持展开的菜单。
2. 点击外侧 AI 输入框并打字：网页菜单保持展开，文字只进入 AI 输入框。
3. 返回网页点击菜单项，或点击网页空白处、按 Esc、按 Tab：网站本身的交互和关闭逻辑正常执行。
4. 反向检查外侧界面的菜单，以及分屏中的两个网页。
5. 切换标签、隐藏和恢复窗口后重复以上动作；agent 操作可见网页期间继续在 AI 输入框打字。

## 根因与工作边界

工作区网页使用独立 `WebContentsView`，外侧界面在主窗口的 `webContents`。原先两者都直接使用系统焦点。用户点击外侧界面时，Chromium 向网页派发元素 `blur` 与窗口 `blur`，网页自身的监听器因而关闭菜单。独立 Electron 页面已复现这一因果链。

另一条同方向干扰来自 agent：指针、键盘、输入、Tab 扫描与拖放之前会调用 `webContents.focus()`，把用户正在输入的区域换成网页。

本地参考 `參考/vscode/src/vs/platform/browserView/electron-main/browserView.ts` 的 `focus()` 与 `setVisible()`：普通聚焦不会主动激活不在前台的窗口，隐藏浏览器视图会把键盘焦点交回工作台；它不将“保留页面状态”解释为不断把系统焦点抢回网页。

[Chrome 官方说明](https://developer.chrome.com/docs/devtools/rendering/apply-effects#emulate_a_focused_page)提供了页面焦点模拟，专门用于保留因切到 DevTools 而消失的菜单等元素；同时明确它会影响 `document.visibilityState`。因此不能对所有后台标签永久开启。

## 实现

- 为当前活动窗口中实际可见的网页和主界面分别保留文档焦点。只在布局或窗口状态变化时同步，不轮询网页、不注入全局事件拦截器。
- 原生键盘焦点继续由实际点击决定。agent 在已隔离页面上使用定向 Chromium 输入，不调用原生 `focus()`；DOM 内部的元素焦点切换仍然有效。
- 网页导航设置 `focusOnNavigation: false`，避免自动加载页面抢走外侧输入焦点。
- 标签隐藏、全局模态遮挡、窗口隐藏/最小化/失活及销毁时撤销模拟并释放 debugger 引用。分屏中所有可见网页可同时保留文档焦点。
- 复用现有共享 debugger，处理启用过程中隐藏/销毁、断连恢复和协议失败；不会关闭其他使用者的 debugger 引用。

这隔离的是不同文档的焦点。操作系统仍然只有一个键盘输入目标。同一网页内部点击别处、失去元素焦点或按 Esc/Tab 的正常行为保留；因鼠标移出、计时器或网站自身状态变化而关闭的浮层，以及系统原生菜单，不承诺由此保持展开。未将同一文档内的编辑器/终端等任意 DOM 区域拆成独立焦点域。

## 验证

- `native-workspace-focus.mts`：真实 Electron 窗口，12 项固定动作回归，包含未修复对照、双向菜单保留、唯一键盘输入目标、分屏、网页内部正常关闭、agent 不抢焦点、iframe、导航、隐藏标签、窗口隐藏与清理。
- `workspace-focus-isolation.test.ts`：7 项生命周期与竞态回归，包括并发启用/隐藏/销毁、共享 debugger、断连恢复、失败回退。
- 新用例已加入 `tools/browser/run-nonvisual.mts`，与现有非视觉输入、上传、拖放、页面地图测试一并运行。
