## 新确认与仍存在的问题

### 1. observe 仍然变成点击：上轮修复不完整

时间线 #45 的原始 `toolOperation.args.effect` 是 `observe`，实际转发宿主的 `input.effect` 已变成 `editDraft`，回执明确 `Observed after click`，用户菜单确实打开。

确定根因在 `crates/lyra-agent-runtime/src/native_backend/tools/host_executor.rs`：

- `coerce_act_effect_to_interaction` 把缺省 interaction 当成非观察动作。
- 当输入 effect=observe 时，直接改写为 editDraft。
- 桌面层收到的已经不是 observe，自然绕过了上轮补的 hover 默认值和观察限制。
- 同文件甚至有 `click_declared_as_observe_uses_the_click` 测试，要求这种转换成功；它与工具目录和桌面层的新契约冲突。

这不是“用户没重启”的解释：本会话已经出现新的任务标签页说明、输入 validity、空终端读取等回执。上轮宿主层／浏览器层的绿色测试没有穿过这段 Rust 转换，不能证明整个调用链正确。修复必须从真实工具入口穿透到实际输入事件，不能继续只测末端。

### 2. 屏幕外＋禁用：状态给到了，前置动作没有串起来

#27 已清楚返回 Authorize 按钮 `disabled`、`offscreen`。agent 没有先显露按钮，而是：等待启用→找复选框→切 AX→再次找复选框→全文和全量地图→网络搜索→刷新→404→重走流程。

从首次发现授权按钮（#27）到最后成功点击（#57），经过 **500.793 秒，约 8 分 21 秒**。

最后 #56 仍是同类状态。#57 的 Lumen 路径先滚动 **395 像素**，按钮中心从 y=808 到 y=413，再读到 enabled 并点击，工具只用 **1.817 秒**，随后 gh 成功。

确定的实现差异：`ax-live-target.ts` 在 `scrollIntoView` **之前**遇到 disabled 就返回；`agent-interaction-executor.ts` 的 Lumen 路径先显露，再校验真实节点状态。相同目标在两条非视觉路径里的准备顺序不一致。

这些证据优先支持“显露／滚动后状态变化没有被利用”。没有当前网页事件监听和脚本执行轨迹，尚不能严格证明 GitHub 只因滚动而启用按钮。正确的下一步是统一显露、重新读取、判断可操作、执行的顺序，并复现可视区域依赖的控件；不能移除 disabled 属性强行点击。
