## 已定位的问题

### 1. 未完成的验证流程没有跨标签页保留，是最关键的绕路起点

第一次在 13:15:41、13:15:51 已依次点了 Send a code via email 和 Verify via email。13:16:06 页面正文明确要求邮件验证码。随后 13:16:23，agent 却把 **同一个 tab-199** 导航到 Gmail，离开了未提交的验证表单。

它用拼接授权 URL、重复进入设备登录来恢复，先遇到 404，再回到默认验证器模式。13:22:41，它把邮件码填进该默认框。工具已明确给出 `invalid=true`、格式错误和六位数字/备用码的 pattern。随后它又在同一页打开 Gmail、无效后退、搜索验证码格式。旧设备码最终过期。

用户纠正后，13:34:39 才把 GitHub 验证表单保留在 tab-205，用另一个 tab-204 读取 Gmail，最终成功。

**责任区分：**主要是 agent 没有维持“任务步骤—标签页—当前验证方式”的对应关系；工具返回没有让待完成流程及预期下一步持续可见，加剧了混乱。最后回复把之前失败概括为“没有切邮箱验证”不完整：第一次切过，是离开该页、重走流程后漏切。

### 2. `effect=observe` 仍然发生点击，且相同误用重复三次

记录 #45、#70、#98（下方采用从 1 开始编号）都传了 `effect: observe`、目标 Authorize 按钮，未传 `interaction`。实际回执是 **Observed after click**，随后再发一次 authorize 点击，就因页面已跳转而 staleTarget。

代码证据：

- `apps/desktop/src/main/agent/lumen-tool-host-helpers.ts:227`：未指定 interaction 默认 click。
- `crates/lyra-tool-fs-core/src/catalog.rs:429`：effect 文案同时要求 observe 用于 hover/focus，声称 mismatches fail closed。
- `apps/desktop/src/main/workbench-browser/view-manager-runtime/agent-action-effect.ts:42`：已有授权 grant 的页面上，可把声明的 observe/navigate 等改判为 authorize/submitExternal。
- `apps/desktop/src/main/workbench-browser/view-manager-runtime/agent-interaction-executor.ts:618`：滚动到目标后刷新元素，再判定 effect 并执行交互。

这些按钮此前显示离屏且禁用；滚动后状态改变。agent 似乎想先让按钮可操作，再点击，但第一步已经点击了。**用户明确要求重新登录，授权本身在用户任务范围内；问题是 API 的观察/点击语义不够一致，不能依赖 agent 每次都猜对组合。**应把“观察/显露目标”和“激活目标”的结果明确区分，并校验声明后果与实际交互，不能仅靠扩大授权范围解决。

### 3. 分格设备码输入存在两类问题

**已确认：两条输入入口不一致。** `input-plan.ts:127` 的 assignments 分支直接 `writeOne`，没有调用单目标分支的 `planSplit`；`input-field-group.ts` 仅按几何尺寸/间距猜分组，`inputFieldFromElement` 没把 maxlength 等语义带入输入规划。

本地直接调用现有生产函数、用虚构字符 `ABCD-EFGH` 验证：同一组八个小输入框，`targetRef + text` 规划为八次单字符写入；`fields: [{targetRef,text}]` 规划为一次九字符写入。这是明确的公共层行为不一致。本会话第一次就从 fields 入口把整段设备码交给第一格，最终报 `input_not_accepted`。后面又把多字符文本交给第一格，仍失败。

**已发生、具体机制待复现：**13:19:42 的合法八格逐格输入，第一格写上、第二格报 `editable_changed`；完全逐格重试又成功。`agent-text-input.ts:95–114` 会检查点击后真实焦点与原目标区域，以及聚焦是否仍停留在目标。日志只能证明故障发生在第二格进入/聚焦阶段，无法分辨网站自动移焦、节点替换、重渲染时序或点击焦点重定向。不能未经实站或等价复现就认定“网站自动跳到下一格导致”。

新输入校验的正面作用已经可见：写入未完整保留会明确报错，而不是声称成功。但**校验能发现失败不等于输入能力已经完整修好**。

### 4. 等待协议容易错过事件，也可能用错误基线提前成功

三次在已进入授权页后调用 `wait(until=textChanged)`，未给 previousText，各耗 29.605、29.553、29.703 秒，合计 **88.861 秒**。返回的正文早已是 Authorize GitHub CLI，工具仍因“等待下一次改变”超时。

`apps/desktop/src/main/agent/lumen-page-wait.ts:23–58` 把第一轮轮询正文作为基线；若前一次动作已经完成跳转，它自然等不到那次变化。另一面，传一个旧页面短语作为 previousText 时，实现把该短语与整个正文比较，即使没有新变化也几乎必然不等。

本地用固定正文调用现有 wait 函数，已确认：不传基线不会匹配；传不等于全文的片段立即匹配；传相同全文不会匹配。代码实现与文档的“整段文本比较”基本一致，但 agent 易把它当“上一次动作完成等待器”。应围绕动作前观察版本/动作后明确结果组织等待；已有 textContains、targetEnabled 等条件在这轮没有被充分使用。

### 5. `Alt+ArrowLeft` 发出去了，但浏览器没有后退

13:17:39、13:25:52、13:27:46 三次回执均 `ok=true`、`pageChanged=false`、`navigationStarted=false`；后续地图/回执 URL 仍留在原页。

`agent-focus-input-controller.ts:696` 的 press 路径只发键盘事件；`agent-keyboard.ts` 将 ArrowLeft 正确转成 Left，但该路径未调用导航历史。`page-registry-controller.ts:659` 的网页键盘监听处理查找和共享控制；现有 `goBack` 是独立能力，没有在此映射中接通。

**本轮后退失败是确定事实；代码定位到浏览器级快捷键与网页按键的能力边界。**返回“按键已发送”并不等于“后退成功”，agent 也没有对明确未改变状态及时换方法。

### 6. 地图能找到元素，但命名、检索、过滤没有保持操作上下文

- `agent-map-presentation.ts:61` 使用整串 includes。`settings profile avatar menu`、`stop send message button`、`Authorize github button checkbox agree` 都无匹配，缩短查询或全量 map 后才能找回。元素并非必然丢失，但检索契约容易误用。

- DeepSeek 账号入口仍是 unnamed div；发送按钮在变为 enabled 后仍带 Message is empty 名称。日志证明名称不理想，但不能仅凭这份保留记录分辨是站点原始命名、tooltip 缓存还是标签合并导致，应补对应 DOM/名称来源证据。
- 查看设置时全文读取包含大量侧栏会话历史。工具成功读取不等于送给模型的信息有助于当前决定。

应优先做到：检索语义明确、无匹配能低成本找回、命中控件保留关联表单/约束/步骤信息、控件名称说明来源及变化。这里不需要引入视觉才有解。

### 7. 输入成功和表单可提交仍混在同一成功结果里

13:22:41 的文字确实写进输入框，所以输入校验成功；但回执同时显示格式 invalid。`lumen-tool-host.ts:688` 只检查输入结果 ok/uncertain，然后执行 thenClick，最后主要保留点击结果，未把表单验证失败作为组合操作的失败状态。

这不是“假输入”，而是**“文字已写入”“格式有效”“提交成功”三个事实没有清晰拆开**。需要在组合输入提交结果里保留每一步状态，并在已知本次输入不合法时避免盲目进入提交步骤。

### 8. 标签页列表、导航回执和实际可读取状态不一致

13:30:45 navigate 报 tab-199 导航成功，13:30:51 map 和之后 wait 都报该 live page 未 materialize。13:31:27 list_tabs 仍把 tab-199 列为 observable，tab-205 才是活动页；显式选择 205 后恢复。

不能说 tab-199 已被关闭，列表证据并不支持。已确认的是**列表“可观察”、导航“成功”和实际读取能力不一致**。是否来自恢复、休眠、视图切换或实例交接，需要主进程生命周期证据，当前不下定论。

终端还留有 another Lyra instance is already using this profile 的日志。它可能与 CLI 启动默认浏览器有关，但现有会话记录不能证明它造成 tab-199 的问题，更不能直接归为整段失败的根因。

### 9. Gmail 首次读取超时会直接打断 wait

13:16:39 read 和 13:34:47 wait 都报 `frame script timed out after 4000ms`；稍后重试恢复。`lumen-page-wait.ts` 对单次 readAgentPage 异常没有在总等待预算内做状态分类重试，局部读取超时直接终止整次等待。

确认的是恢复契约不足；仅凭日志无法判断 4 秒超时来自页面加载、框架重建、脚本执行阻塞还是 frame 生命周期，不应先扩大所有超时。

### 10. 模型长推理和额外往返放大了上述问题，不能直接认定是 VPN

前两个任务模型调用中位数约 6.55 秒、6.84 秒；登录阶段中位数约 8.01 秒，纠正后约 8.25 秒。纠正前最后五次调用耗时共 **336.064 秒**，单次最长 **126.574 秒**；最长这次输出 4239 tokens，其中 4180 为 reasoning。这里展示的是计量，不展示内部推理内容。

说明大量时间确实用来生成推理，不是工具在页面上执行了两分钟。设备码失败后持续重新理解、搜格式、再后退，让一个简单步骤越来越长。

上下文输入从会话开始的 16459 tokens 增至最后的 124676；登录开始为 46079。重复观察、历史和重试累积值得处理，但大多数调用有缓存命中，而且 12 万上下文下仍有较短调用，不能断言“上下文长度就是全部慢的原因”。

另有一次约 30.064 秒 provider transport_error 后安全重试。它可能包含网络因素；现有数据没有 VPN 开关对照、首 token 时间和分段传输记录，无法判定 VPN/TUN 因果。把这一轮全归为网络慢不符合证据。
