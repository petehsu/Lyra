## 已定位的问题

### G1：附件通路没有闭合，系统却让 agent 继续寻找原生窗口

**状态：确定的实现缺口；隔离复现成功。**

实际会话第 27 次调用点击 `Attach files`，收到 `inputDelivery=targetReceived`。这只能证明按钮收到真实输入，不能证明文件选择、上传或附件完成。随后 agent 查询桌面窗口，前台是 v2rayN；可访问应用列表中没有 Lyra 的文件选择窗口。之后搜索上传工具无结果，最后被用户停止。

代码中的三处断点：

1. `apps/desktop/src/main/workbench-browser/cdp-audit-session.ts:419` 主动开启 `Page.setInterceptFileChooserDialog({enabled:true})`。Chrome 官方协议明确说明，启用后原生文件窗口不显示，改为发出 `Page.fileChooserOpened`。[Chrome 官方协议定义](https://github.com/ChromeDevTools/devtools-protocol/blob/master/types/protocol-proxy-api.d.ts)
2. 同文件第 346 行处理事件时只调用无参通知。事件提供的 `backendNodeId / frameId / mode` 没有传入后续上传链。产品目录中未找到 `DOM.setFileInputFiles`；实际会话的工具搜索也找不到上传工具。
3. `agent-observation-runtime.ts:522` 先筛选“可见且未禁用的 file input”，只有找到它才上传 `active_file_chooser` 信号。常见的“可见附件按钮 + 隐藏 file input”会漏掉状态，即使 CDP 已经知道选择器请求存在。消息使用“system file picker”也掩盖了它已被拦截的事实。

独立 Electron 43.6 诊断使用当前生产代码的审计、点击、状态存储及地图逻辑：点击一个触发隐藏 file input 的附件按钮后，CDP 事件 1 次，携带三种节点/框架/模式字段；内部 `pending=true`、点击成功且 `targetReceived`；地图没有 chooser 信号，`blockedRegions=[]`。这复现了“宿主知道，agent 看不到”的断层。

会话未保留当时的原始 CDP chooser 事件，不能把隔离实验的事件当成 Gmail 当时的事件。但源码、已构建代码、官方协议、会话中的症状和隔离复现一致，足以确认当前通路有结构性缺口。

修复应以“点附件 → 得到明确待选文件状态 → 选择授权文件 → 页面出现已上传附件”为整体契约；无上传能力时立即报告不能完成，不能继续建议寻找被系统隐藏的窗口。浏览器文件输入接口本身仍是非视觉网页操作，不等于绕过网页调用 Gmail 业务 API。

### G2：iframe 的页内导航覆盖主标签页网址

**状态：会话现象已确认，代码根因已定位，Electron 事件行为已复现。**

第 2 次工具结果的标题和内容属于 Gmail 草稿页，但 `url` 变成 `https://contacts.google.com/widget/hovercard/v/2?...`，这是嵌入的联系人组件。

`page-registry-controller.ts:525` 的 `did-navigate-in-page` 监听器只接收 `_event, url`，不检查第三个参数 `isMainFrame`，直接 `syncAddress(url)`，并清空整个页面的目标缓存。`agent-target-runtime.ts:5` 又优先读取这个 runtime 地址，导致后续读取接口把子框架地址报告为当前标签页地址。

Electron 官方说明此事件可来自任意 frame，并提供 `isMainFrame`。[Electron webContents 文档](https://www.electronjs.org/docs/latest/api/web-contents#event-did-navigate-in-page)

隔离实验：主页面是 `/main`，iframe 改 hash 为 `/child#child-change`，事件返回 `isMainFrame=false`，同时 `webContents.getURL()` 仍是 `/main`。当前监听器会把这个子页面地址传给 `syncAddress`。

本次没有证据显示 agent 实际切错标签页；已经发生的是标签页身份元数据污染。缓存失效、地址恢复及后续导航判断受影响属于从代码推导的风险，不作为本次已发生的结果。

### G3：正文已经实际写入，却收到“未保留文本”的失败回执

**状态：状态矛盾和恢复绕路已确认；Gmail 精确触发条件尚未完全复现。**

第 9 次调用在一次 `fields` 输入中写主题和正文，正文有 92 个字符（去掉换行后 81 个）。工具返回 `input_not_accepted`，说明“编辑器没有保留请求文本”。但没有再次输入正文，第 11 次地图已有正文内容、光标偏移 81；后续保存、重开及格式操作都继续使用这份正文。

因此不能按“没有写入”指导重试，自动重复输入还可能造成内容重复。当前错误返回没有区分“文本不匹配”和“没有采集到接受事件”，也没返回失败正文的实际值，定位证据不足。

`agent-text-input.ts:171–176` 将值比较不符和输入事件未接受统一成同一种错误；`agent-focus-input-controller.ts:135` 在输入后等待 30ms 就验证。候选原因包括编辑器异步处理、输入事件观测和 Gmail 特有内容转换；本次不将任何一个候选写成已证实根因。

我用当前生产输入控制器，在独立 Electron 窗口中输入同一段文本：空 contenteditable、带初始 `<br>` 的 contenteditable 都通过。因此“多行文本必然校验失败”这个解释不成立。另一个独立隐患是现有 canonical 比较删除所有换行，不能单凭该比较证明段落结构保持正确。

恢复接口也存在歧义：第 10 次 `read(query="Message Body")` 是全文查找，不是读取该名称输入框的值，所以返回 0 条；agent 到第 11 次 `map` 才找回真实状态。失败到正确读取约 19 秒，包含两次额外模型往返。

### G4：编辑器内容被误当成一组独立操作控件

**状态：真实会话和生产地图隔离复现均确认。**

第 25 次操作后第一页地图展示 26 项，其中 14 项是正文里的段落、空行及 `b/i/u` 子节点；真正的 `Attach files` 没出现在这页，agent 需要另查。第 32 次宽泛搜索匹配 51 项，第一页 23 项仍被这些内容占据。

`agent-observation-runtime.ts:106,284,717` 把 `isContentEditable=true` 当作输入控件/原生控件条件。但正文后代继承该属性，普通段落及格式节点也会被收录并赋予 `targetRef`、`editable=true`；空段落甚至提示“无名 div，可 hover 找 tooltip”。

隔离实验使用生产观察引擎，仅一个主题框和一个富文本编辑器，输入后地图却返回 13 项：两个实际字段加 11 个段落/空行。

需要从“独立可操作对象”的边界收敛到编辑宿主，正文和选区格式作为该编辑器的状态。不能简单删除所有 div/b/i/u：真实嵌套按钮、独立可聚焦组件仍需保留。此问题应在采集归属层解决，不能靠让 agent 忽略一串假控件。
